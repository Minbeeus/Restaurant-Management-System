# AI Agent Coding Conventions

> **Rule Hierarchy Level:** 16
> **Applies To:** AI Coding Agents (Antigravity, Cursor, etc.)
> **Last Updated:** 2026-07-14

## Purpose
This document defines the strict execution boundaries, behavioral protocols, and quality standards that all AI Coding Agents MUST follow when analyzing, editing, or generating code in this repository. It acts as the primary governing convention for agent behavior.

## Scope
This convention applies exclusively to the reasoning patterns, file manipulation choices, validation routines, and output formats generated by AI Coding Agents. It references and enforces all prior technical conventions.

## Principles
1. **Purity of Context:** AI agents must understand existing patterns before editing.
2. **Minimal Invasiveness:** Never introduce changes, files, or packages outside the direct scope of the user request.
3. **Reusability Over Recreation:** Treat duplication as a failure. Existing code, components, and services are the default building blocks.
4. **Validation Integrity:** All changes must be programmatically verified (compiled and tested) before being reported.

---

## Mandatory Rules

### AGENT-001: Pre-Edit Code Research
Before editing any file, the agent MUST locate and read the target file, its dependencies, its interfaces, and any relevant conventions (e.g., UI, Security, Database) to understand the existing architectural patterns. Coding based on assumptions of a file's content without reading it is strictly prohibited.
- **Rationale:** Prevents breaking existing class designs, conventions, or duplicate implementation of existing helper methods.
- **Consequence:** Modifying files blindly results in compilation errors, broken API contracts, and redundant methods.

### AGENT-002: Strict Reuse of Components and Code
The agent MUST NOT generate duplicate logic, duplicate helper functions, or duplicate UI markup.
- For UI tasks: The agent MUST search the project for existing components and CSS structures, and reuse them.
- For business logic tasks: The agent MUST reuse existing services, repositories, validators, and mapping configurations.
- If a required feature is similar to an existing one, the agent MUST extend the existing implementation rather than writing a new one.
- **Rationale:** Enforces DRY, keeps the codebase small, and simplifies system maintenance.
- **Consequence:** Generating copy-pasted buttons, cards, or services bloats the repository and divides the design system.

### AGENT-003: Strict SOLID Compliance
All code generated by the agent MUST strictly conform to the 5 SOLID principles.
- **SRP:** Each class or service MUST handle only a single responsibility. Do not create or add to "God" classes.
- **ISP:** Do not force classes to implement methods they do not use. Split large interfaces (e.g., separate `IOrderReadService` and `IOrderWriteService` instead of a monolithic `IOrderService`).
- **Rationale:** Ensures the codebase remains modular, testable, and maintainable.
- **Consequence:** Violating SOLID makes refactoring impossible and causes cascade failures when interfaces change.

### AGENT-004: Zero Hardcoded Text and Magic Strings
The agent MUST NOT introduce string literals for user-facing UI text, error messages, notifications, or magic status strings in logic code.
- All UI text and user-facing messages MUST be loaded from resource files (`.resx`, JSON translations, etc.).
- All configuration values, security endpoints, and API paths MUST be retrieved from app configuration classes or environment variables.
- Technical/business constants MUST be defined in centralized constants classes or enums at the Domain layer.
- **Rationale:** Guarantees localized multi-language compatibility and prevents security credentials from leaking into Git.
- **Consequence:** Hardcoded strings require source edits to translate and trigger security alerts during audits.

### AGENT-005: Clean Architecture Boundaries
The agent MUST respect layer boundaries.
- **Domain Layer:** MUST NOT depend on any other layers or external libraries (except core system libraries).
- **Application Layer:** MUST depend only on the Domain Layer. MUST NOT reference EF Core, SQL Server, or Web API namespaces.
- **Infrastructure Layer:** The sole location for database configurations, repository implementations, and external system integrations.
- **Presentation/Web API Layer:** Receives requests and delegates immediately to Application Services. MUST NOT contain business logic.
- **Rationale:** Keeps business logic pure and technology-agnostic.
- **Consequence:** Referencing database libraries in the application or domain layers prevents switching database engines or frameworks.

### AGENT-006: UI Component-First Rule
When writing frontend templates (e.g., Blazor, MVC views, HTML layouts), the agent MUST use reusable components rather than writing inline HTML/CSS blocks.
- Building custom visual elements directly inside views using raw, ad-hoc CSS is prohibited.
- Any new visual block (e.g., meal cards, invoice rows) MUST be designed as a modular component using BEM styling patterns.
- **Rationale:** Ensures styling changes can be made globally in one place.
- **Consequence:** Ad-hoc frontend structures lead to visual inconsistencies across views.

### AGENT-007: Confirmation Modal for Destructive UI Actions
When generating UI actions that delete, cancel, or disable entities, the agent MUST implement a confirmation modal. Binding destructive operations directly to a button's primary click event without a confirm state is strictly prohibited.
- **Rationale:** Safe-guards users against accidental data destruction.
- **Consequence:** Immediate deletion on button click causes frequent user errors.

### AGENT-008: Clarification Protocol
If a user request is ambiguous, lacks specific parameters, or contradicts business rules documented in specifications, the agent MUST stop and ask the user for clarification. Making assumptions about business logic is prohibited.
- **Rationale:** Ensures accuracy of domain business logic and prevents wasted code churn.
- **Consequence:** Guessing business logic leads to incorrect behavior and system bugs.

### AGENT-009: CLI Compile & Test Verification
Before declaring a task finished, the agent MUST run compilation (`dotnet build` or equivalent) and unit testing (`dotnet test` or equivalent) commands. 
- The agent is permitted up to 3 automatic retry attempts to resolve syntax, compile, or test failures.
- If errors persist after 3 attempts, the agent MUST halt execution and present a detailed compiler error report to the user.
- **Rationale:** Guarantees that code introduced by the agent is syntactically correct and passes all tests before handoff.
- **Consequence:** Code that does not compile breaks the build pipeline for other developers.

### AGENT-010: Database Migration Review
When modifying entities, the agent MUST NOT run database updates automatically in production. The agent MUST generate a migration (`dotnet ef migrations add`), and then run the SQL generation script (`dotnet ef migrations script`) to inspect the generated SQL for anomalies (such as drop table operations) before presenting it to the user.
- **Rationale:** Protects live databases from catastrophic schema changes.
- **Consequence:** Auto-running migrations can cause data loss.

### AGENT-011: Output Format (Diff-Only)
When printing code changes in the chat transcript, the agent MUST output diff-only formats showing the added/removed code blocks with context. Printing full file contents is prohibited unless creating a new file or performing a total file refactor.
- **Rationale:** Saves token context and makes it easy for the user to review edits.
- **Consequence:** Printing full files wastes context and obscures the exact changes.

## Recommended Practices

### AGENT-050: Document Assumptions
If the agent must make minor assumptions due to missing technical parameters (excluding business logic), it SHOULD explicitly document these assumptions in the final task report.
- **Rationale:** Alerts the user to decisions that might need adjustments later.

## Anti-patterns

### Blind Code Generation
Generating functions without first checking if the helper class or library is already imported or exists.
- **Why it's harmful:** Creates name collisions, duplicate logic, and compiler warnings.
- **What to do instead:** Use search tools (e.g., `grep_search`) to locate keywords before writing code.

### Silent Command Failure
Running a build command, seeing warnings or minor test failures, and ignoring them in the final report.
- **Why it's harmful:** Degrades codebase health over time.
- **What to do instead:** Fix all compiler warnings and test failures before completing the task.

## Examples

### ✅ Correct (Follows pre-research, compilation checks, SOLID)

**Agent Execution Step:**
1. User requests adding validation to an email input.
2. Agent searches codebase for validator class: `grep_search` on `Validator`.
3. Agent reads the target validator file and finds `CreateUserCommandValidator`.
4. Agent edits only that file using `replace_file_content` to add email validation rules.
5. Agent runs `dotnet build` and `dotnet test` to confirm success.
6. Agent reports changes using a concise diff and structured summary.

### ❌ Incorrect (Creates duplicate helper, uses hardcoded strings, prints full file)

**Agent Action:**
Instead of reading existing files, the agent writes a custom regex validator directly inside the Controller method using a hardcoded error message `"Email không hợp lệ"`, compiles nothing, and prints the entire 500-line controller file in the chat.

## Checklist
- [ ] Have you read the target file and verified existing helper patterns before making changes?
- [ ] Have you confirmed that the changes follow SOLID principles (especially SRP and ISP)?
- [ ] Are all new UI elements built as reusable components rather than inline HTML blocks?
- [ ] Do all destructive actions require confirmation modals?
- [ ] Have all strings, error messages, and UI text been moved to localization/resource structures?
- [ ] Did you run build and test scripts locally, and did they pass successfully?
- [ ] Is your final output formatted as a concise diff with a structured task summary?
